# Butterfly QA 技术设计与交接说明

## 1. 系统定位

Butterfly QA 是一个面向测试流程的本地 Agent 编排原型。它的重点不是让模型自由完成所有工作，而是用代码约束 Agent 的输入、输出、权限、状态和产物追溯。

V1 当前覆盖：

- 需求导入和不可变源文件保存。
- 需求评审、需求分析、测试点与功能测试用例设计、用例评审。
- 人工审批、人工执行结果录入和测试证据管理。
- 测试报告生成、Markdown 渲染和报告审批。
- Agent 调用审计、有限重试、超时检测和人工接管。
- FastAPI/Vue Web 工作台、文件预览、执行录入和审批回退。

V1 暂不覆盖接口自动化、UI 自动化、RAG、数据库和外部测试管理平台。

## 2. 运行架构

```text
Web 工作台 / CLI / 调用方
    |
    v
FastAPI API（Web 请求）
    |
    v
Python Harness
    |
    +-- WorkflowOrchestrator 负责一次流程步进
    +-- WorkflowStateMachine 负责合法状态转换
    +-- ResilientAgentRunner 负责超时、重试和审计
    +-- CodexAgentRunner 负责真实 Codex 调用
    |
    +-- 结构化 Schema 校验
    +-- ArtifactStore 版本化保存产物
    +-- EvidenceService 校验证据完整性
    |
    v
本地 projects/<project-id>/ 目录
```

一次 Agent 调用分为两层：

1. 主流程 Agent 返回 `WorkflowAction`，决定下一步是调用哪个 Agent、等待人工还是推进状态。
2. 专业 Agent 返回结构化产物，Harness 校验通过后才保存并更新活动产物。

专业 Agent 不直接互相调用，也不负责修改工作流状态。

## 3. Agent 和 Skill 边界

### Agent

- `main-flow-agent`：流程路由、状态判断、人工等待和最终测试报告调度。
- `test-analysis-design-agent`：需求评审、需求分析、测试点和功能测试用例设计。
- `testcase-review-agent`：独立评审测试用例的完整性、正确性和风险覆盖。

### Skill

- `requirement-review`：识别需求歧义、遗漏、冲突和不可测试项。
- `requirement-analysis`：提取需求条目、流程、状态、权限和业务规则。
- `testcase-design`：从需求分析生成测试点和功能测试用例。
- `testcase-evaluation`：独立检查用例质量和覆盖风险。
- `test-report`：根据执行记录和证据生成测试报告。

Agent 是职责和权限边界，Skill 是当前任务的专业方法。一个 Agent 可以在不同阶段调用多个 Skill，因此没有为每个 Skill 单独创建 Agent。

## 4. 核心代码模块

| 模块 | 作用 |
| --- | --- |
| `src/qa_agent/schemas/models.py` | 定义需求、测试设计、执行、报告和证据模型 |
| `src/qa_agent/workflow/` | 定义状态、合法转换和持久化工作流模型 |
| `src/qa_agent/orchestrator.py` | 执行一次主流程决策和专业 Agent 交接 |
| `src/qa_agent/agent_protocol.py` | 定义 Agent 请求、响应和 WorkflowAction 协议 |
| `src/qa_agent/codex_runner.py` | 将协议适配到 `openai-codex` SDK |
| `src/qa_agent/audit.py` | 记录每次 Agent 尝试并处理重试、超时 |
| `src/qa_agent/storage/artifact_store.py` | 保存不可覆盖的版本化产物和工作流文件 |
| `src/qa_agent/evidence.py` | 导入证据、生成清单、校验 SHA-256 和大小 |
| `src/qa_agent/human_actions.py` | 处理人工审批和人工执行结果 |
| `src/qa_agent/reporting.py` | 汇总执行结果并渲染 JSON/Markdown 报告 |
| `src/qa_agent/cli.py` | 提供本地命令行入口 |
| `src/qa_agent/web/` | 提供统一 HTTP API并托管生产前端资源 |
| `frontend/` | Vue Web 工作台源码 |

## 5. 项目目录和产物

```text
projects/<project-id>/
├── project.json          # 项目清单和原始输入元数据
├── workflow.json         # 当前状态、活动产物和转换历史
├── input/                # 不可覆盖的需求、设计图和附件
├── artifacts/            # 结构化产物及 Markdown 渲染
├── evidence/             # 测试证据文件和证据清单
├── decisions/            # 人工审批记录
└── agent-runs/           # Agent 每次调用审计记录
```

所有产物使用稳定 ID 和版本号。新的修订应产生新版本，不覆盖旧版本。

证据导入后会保存 SHA-256、文件大小和媒体类型。验证时优先使用项目中的证据清单，即使执行记录没有携带哈希，也能发现文件被篡改。

## 6. 运行方式

推荐使用一键安装脚本。默认创建独立的 `butterfly-qa` Conda 环境，同时安装依赖并持久化 UTF-8 配置：

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1
conda activate butterfly-qa
```

复用已有环境：

```powershell
powershell -ExecutionPolicy Bypass -File .\install.ps1 -EnvironmentName py310
conda activate py310
```

日常使用优先启动一体化 Web 工作台：

```powershell
butterfly-qa web
```

默认地址是 `http://127.0.0.1:8000/`。生产前端已包含在 Python 安装包内，使用者不需要安装 Node 或分别启动前后端。以下 CLI 命令主要用于开发调试和自动化脚本。

创建项目并导入需求：

```powershell
butterfly-qa project create address-change --name "修改收货地址" --created-by tester-001
butterfly-qa input add address-change .\requirement.md --category requirement --imported-by tester-001
```

导入证据：

```powershell
butterfly-qa evidence add address-change .\failure.png --type screenshot --description "失败截图"
butterfly-qa evidence add address-change .\service.log --type log --description "服务日志"
```

执行一步 Agent 流程：

```powershell
butterfly-qa run address-change
```

人工审批和执行结果录入：

```powershell
butterfly-qa approve address-change --type testcase --decision approved --by tester-001
butterfly-qa execution submit address-change .\execution.json
butterfly-qa approve address-change --type report --decision approved --by tester-001
```

## 7. 真实 Codex 联调说明

真实 CLI 调用依赖：

1. `openai-codex` 已安装到当前 Python 环境。
2. 当前环境已经完成 Codex 登录或认证配置。
3. 运行命令时，工作目录是项目仓库根目录，能够读取 `agents/`、`skills/` 和项目文件。
4. Agent 输出必须是对应 Schema 的 JSON，不能只返回解释性自然语言。

真实调用使用只读沙箱。Agent 可以读取项目输入和产物，但不能直接修改项目文件，也不能自行推进工作流状态。真实联调前建议先使用 `tests/` 中的替身测试确认代码链路，再进行小需求试跑。

## 8. 当前限制和后续方向

- 当前报告是 Markdown 和 JSON，没有接入测试管理平台。
- 当前只支持本地文件证据，尚未实现图片脱敏和在线对象存储。
- 当前 Agent 是顺序调用，尚未针对耗时任务引入并行调度。
- 接口自动化应作为独立 Agent，主要输入应是接口文档和已确认用例，而不是只依赖需求文档。
- 真实 Codex 输出质量仍需使用团队真实需求持续评估，结构化校验不能替代业务人员审批。
