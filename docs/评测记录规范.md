# Butterfly Agent 评测记录规范

> 用于记录 Butterfly Agent 测试 WhaleTestPro 时的版本、产出质量和黑盒验证结果。

## 1. 记录目标

本规范只记录三件事：

1. 本次评测使用了什么版本的被测系统和 Agent。
2. Agent 的产出是否准确、可执行、可追溯。
3. APITest 或人工执行是否验证了这些判断。

不要把“记录过程”变成新的手工测试工作。Agent 已经保存的技术信息不需要再次抄写。

## 2. 三类记录的边界

| 记录内容 | 负责人 | 是否手动填写 |
| --- | --- | --- |
| 调用 ID、请求和最终响应 | Agent | 否 |
| Agent 角色、Skill、模型、线程、时间和耗时 | Agent | 否 |
| 成功、失败、超时、重试和人工接管 | Agent | 否 |
| 工作流状态和状态迁移历史 | Agent | 否 |
| 需求、分析、用例、报告的版本 | Agent | 否 |
| 输入文件、证据文件及 SHA-256 | Agent 保存；导入动作由人发起 | 只需确认已导入 |
| WhaleTestPro Git 版本 | 人工 | 是 |
| WhaleTestPro-APITest Git 版本 | 人工 | 是 |
| Butterfly Agent、Prompt、Skill、Schema 版本 | 人工 | 是 |
| 测试模块和本次改动目的 | 人工 | 是 |
| 问题是否有效、是否误报或漏报 | 人工 | 是 |
| 用例是否可直接使用、人工修改内容和耗时 | 人工 | 是 |
| APITest 通过、失败、跳过和发现的问题 | pytest 产生结果；人工做对照统计 | 是 |
| Agent 与 APITest 的重合、独立发现和漏测 | 人工 | 是 |

Agent 的自动记录主要落在项目目录下：

```text
projects/<project-id>/agent-runs/
projects/<project-id>/artifacts/
projects/<project-id>/workflow.json
projects/<project-id>/evidence/
```

当前 Web 工作台展示的是工作流审计流；完整的 Agent 请求、响应和重试记录需要查看 `agent-runs` 文件。

## 3. 每次运行记录一行

建议使用 Excel、Markdown 表格或 CSV，维护一张“运行记录”表。每次完成一个模块的 Agent 流程后填写一行。

| 日期 | WhaleTestPro 版本 | Agent 版本 | 模块 | 需求问题有效数/总数 | 用例可用数/总数 | 人工耗时 | APITest 失败数 | Agent 漏测数 | 结论 |
| --- | --- | --- | --- | --- | --- | ---: | ---: | ---: | --- |
| 2026-08-28 | v1 | v1.0 | 成员权限 | 5/7 | 18/24 | 25 分钟 | 3 | 1 | 需优化权限场景 |

字段含义：

- **需求问题有效数/总数**：Agent 报告的问题中，经人工确认有效的问题数和总数。
- **用例可用数/总数**：无需修改即可执行的用例数和 Agent 生成的用例总数。
- **人工耗时**：检查和修订 Agent 产物的时间，不含实际接口执行时间。
- **Agent 漏测数**：APITest 或人工发现、但 Agent 产物没有覆盖的问题数量。
- **结论**：使用“可直接使用”“需修订”“不可用”即可。

前期记录原始数量，不要急着填写过度精确的百分比。例如记录 `6/8`，比记录 `75%` 更容易复核。

## 4. 只有出现问题时才建问题记录

没有问题的运行不需要写长篇总结。发现有价值的问题时，在“问题记录”表中增加一行。

| 问题 ID | Run ID | 来源 | 类型 | 严重程度 | Agent 是否发现 | 证据 | 处理结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| BUG-001 | run-001 | APITest | 水平越权漏测 | High | 否 | APITest 报告 | 加入 Golden Set |

问题类型建议使用：漏测、误报、编造规则、断言过弱或错误、追溯错误、流程或结构错误。

## 5. APITest 执行后的对照统计

先运行独立的 WhaleTestPro-APITest，再把结果和 Agent 产物对照。重点记录三组数字：

```text
Agent 发现且人工确认有效的问题
Agent 和 APITest 都发现的问题
APITest 发现但 Agent 漏掉的问题
```

示例：

```text
APITest：通过 48，失败 3，跳过 1
重合问题：2
Agent 独立发现：1
Agent 漏测：1
修复后回归：通过
```

APITest 不能替代需求基线。需求评审的准确率和召回率，仍需要人工确认的“有效问题清单”作为基准。

## 6. 每个 Agent 版本写一次总结

当 Prompt、Skill、Schema 或流程代码发生变化时，写一份简短总结：

```text
Agent 版本：v1.2
本次改动：增强权限和边界场景提示词
测试模块：认证、项目成员、接口管理
运行次数：6
主要改善：权限漏测减少，人工修改时间下降
主要问题：复杂异步场景仍需要人工补充
结论：保留 v1.2，继续优化异步任务覆盖
```

如果 WhaleTestPro、APITest、需求文档或模型同时变化，应在总结中说明，不能把所有变化都归因于 Agent。

## 7. 推荐的评测顺序

先从三个模块建立基线：

1. **认证与项目成员**：权限、越权、Token、边界。
2. **测试用例与场景**：链路、变量传递、数据准备、异常分支。
3. **Mock、报告与回归**：契约、异步结果、报告追溯和回归范围。

每个模块按以下流程执行：

```text
需求导入
→ 需求评审
→ 需求分析
→ 测试点和功能用例
→ 独立用例评审
→ 人工确认和修订
→ 人工执行或 APITest 验证
→ 导入证据
→ 生成报告
```

前期每个模块运行 3～5 次即可发现主要问题。等记录稳定后，再计算准确率、召回率和版本趋势。

## 8. 评价原则

- 不把结构化输出通过当成测试质量通过。
- 不把用例数量当成覆盖质量。
- 不把一次运行结果当成稳定结论。
- 不把 APITest 失败全部归因于 Agent，要区分环境、数据和被测系统缺陷。
- 高严重级别漏测、编造业务规则和无证据结论必须单独标记。
