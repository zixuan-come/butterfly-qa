# 测试全流程 Agent 系统需求文档

- **文档状态**：V0.1 讨论稿
- **编写日期**：2026-08-21
- **目标平台**：Codex
- **适用阶段**：V1 本地可运行原型

## 1. 文档目的

本文档用于统一测试全流程 Agent 系统的目标、范围、角色边界、流程规则、输入输出和验收标准，作为后续方案设计、开发、测试和项目交接的共同依据。

本文档描述的是“做什么”和“做到什么程度”，不替代后续的技术设计文档。具体的 Python 模块、Prompt 细节、Skill 文件内容和部署方式，在技术设计阶段另行确定。

## 2. 项目概述

### 2.1 项目背景

在日常测试工作中，需求评审、需求分析、测试点提取、功能测试用例设计、用例评审、测试执行和测试报告之间存在大量重复性工作。当前工作还容易出现以下问题：

- 需求中的歧义、遗漏和不可测试内容没有在测试设计前被充分暴露。
- 测试点、前置条件、测试数据和预期结果不完整，导致用例质量不稳定。
- 用例设计者和评审者缺少独立性，容易出现“自己写、自己认可”。
- 流程依赖个人记忆，返工、跳步和产物丢失难以追踪。
- AI 输出如果没有结构化校验、权限边界和人工审批，可能产生不可控修改。

### 2.2 产品定位

本系统是一个基于 Codex 的测试流程编排系统。它通过一个主流程 Agent 协调两个专业 Agent，并由多个 Skill 承担具体工作，将需求资料逐步转化为：

```text
需求评审报告
    -> 结构化需求分析
    -> 测试点与功能测试用例
    -> 用例评审报告
    -> 人工执行记录
    -> 测试报告
```

系统的核心不是让 AI 自主替代测试人员，而是让测试过程具备清晰的分工、可控的审批、结构化的产物和可追溯的过程记录。

## 3. 目标与成功标准

### 3.1 V1 目标

V1 应支持测试人员在本地完成一个需求从接收到测试报告生成的完整闭环：

1. 导入需求文档及相关资料。
2. 自动进行需求评审并输出问题清单和准入结论。
3. 对通过评审的需求进行结构化分析。
4. 生成测试点和功能测试用例。
5. 由独立的用例评审 Agent 进行质量评估。
6. 支持评审不通过后的修订和重新评审。
7. 支持人工确认用例、人工执行用例并录入执行结果和证据。
8. 根据执行结果生成测试报告。
9. 保存所有中间产物、版本、决策和审批记录。

### 3.2 成功标准

- 流程不会因为上下文过长或对话中断而丢失当前阶段和已有产物。
- 每个阶段都有明确的输入、输出和完成条件。
- 需求评审不通过时，系统不会直接进入测试用例设计。
- 用例评审 Agent 与用例设计 Agent 相互独立，避免直接复用设计结论作为评审结论。
- 任何对正式需求的修改都必须由人完成，系统只能输出澄清清单和修改建议。
- 测试报告能够追溯到需求、测试用例、执行结果和测试证据。
- 使用一个小型真实需求可以跑通完整闭环及主要回退路径。

## 4. V1 范围

### 4.1 纳入范围

- 需求文档读取和项目资料整理。
- 需求评审。
- 需求分析。
- 测试点提取。
- 功能测试用例设计。
- 测试用例独立评审。
- 测试用例修订和重新评审。
- 人工确认测试用例。
- 人工录入测试执行结果。
- 测试报告生成。
- 本地文件存储、版本记录和流程状态记录。
- JSON 结构化数据协议和 Markdown 可读报告。

### 4.2 暂不纳入范围

以下能力不作为 V1 的交付条件：

- 接口自动化代码生成和自动执行。
- UI 自动化代码生成和自动执行。
- 自动修改正式需求文档。
- 自动访问生产环境或真实生产数据。
- Jira、禅道、飞书、企业微信等外部系统接入。
- Web 管理后台和多人在线协作界面。
- 向量数据库、RAG 知识库和复杂长期记忆系统。
- 多任务并行调度和大规模分布式执行。
- AI 自动决定是否发布或替代人工发布审批。

> 接口自动化未来作为独立 Agent 设计。它的主要输入应是已确认的测试用例、Swagger/OpenAPI 或其他接口文档、测试框架、环境配置和测试数据，而不是只依据需求文档生成代码。

## 5. 用户与角色

### 5.1 主要用户

**测试/测试开发工程师**：导入需求、查看分析结果、确认和修订测试用例、执行测试、补充证据、生成测试报告。

### 5.2 业务协作角色

**产品经理或需求提供方**：查看需求评审问题，补充或修改正式需求，并重新提交评审。

**测试负责人**：确认用例范围、风险接受情况和最终测试结论。

### 5.3 系统角色

系统采用 3 个 Agent，具体职责如下：

| Agent | 核心职责 | 可使用能力 | 不负责的事情 |
| --- | --- | --- | --- |
| 主流程 Agent | 流程编排、状态流转、审批等待、回退重试、产物保存和最终汇总 | 测试报告生成 Skill；流程控制能力 | 不直接承担需求分析和用例编写 |
| 测试分析与设计 Agent | 需求评审、需求分析、测试点提取、功能用例设计和用例修订 | 需求评审 Skill、需求分析 Skill、测试点与测试用例设计 Skill | 不负责独立评审自己的用例 |
| 用例评审 Agent | 独立检查测试用例的完整性、正确性、可执行性和风险覆盖 | 测试用例评估 Skill | 不负责设计用例或直接修改用例 |

所有 Agent 的调用、交接、回退和重试都由主流程 Agent 统一编排，两个专业 Agent 不直接互相调用。

## 6. Agent 与 Skill 设计

### 6.1 Skill 清单

| Skill | 输入 | 输出 | 关键要求 |
| --- | --- | --- | --- |
| 需求评审 Skill | 需求文档、设计资料、已有约束 | 需求评审报告 | 识别歧义、遗漏、冲突、不可测试项和风险；给出准入结论 |
| 需求分析 Skill | 已通过评审的需求资料 | 结构化需求分析 | 明确参与者、业务规则、流程、状态、数据、异常和边界 |
| 测试点与测试用例设计 Skill | 结构化需求分析及相关资料 | 测试点、功能测试用例 | 测试点与用例关联；覆盖正常、异常、边界、权限、状态和兼容性等场景 |
| 测试用例评估 Skill | 测试点、测试用例、需求分析 | 用例评审报告 | 保持独立评审；输出问题等级、定位、理由和修改建议 |
| 测试报告生成 Skill | 执行记录、缺陷、阻塞项、截图、日志等证据 | 测试报告 | 结论必须基于执行数据和证据，不得凭空补充结果 |

### 6.2 测试点与测试用例的关系

测试点不作为单独 Agent 或单独流程节点。V1 中，测试点是测试用例设计产物中的结构化字段，并与一个或多个测试用例建立关联：

```text
需求条目 -> 测试点 -> 测试用例 -> 执行记录 -> 测试报告结论
```

这样既保留测试分析的思考过程，又避免为了一个紧邻的步骤额外拆分 Agent。后续如果需要测试点复用、覆盖率分析或跨项目回归，再考虑将测试点抽成独立能力。

## 7. 业务流程

### 7.1 主流程

```text
接收需求文档
  -> 需求评审
  -> 判断是否满足测试设计准入条件
  -> 需求分析
  -> 测试点与功能测试用例设计
  -> 独立用例评审
  -> 人工确认测试用例
  -> 人工执行测试并记录证据
  -> 生成测试报告
  -> 流程结束
```

### 7.2 需求评审不通过

```text
需求评审不通过
  -> 输出澄清清单、风险和修改建议
  -> 等待产品或需求提供方修改正式需求
  -> 重新接收需求
  -> 重新需求评审
```

系统不得擅自修改正式需求，也不得在需求不满足准入条件时继续生成正式测试用例。

### 7.3 用例评审不通过

```text
用例评审不通过
  -> 输出评审报告
  -> 主流程 Agent 发起修订
  -> 测试分析与设计 Agent 根据问题修改用例
  -> 重新提交用例评审
```

### 7.4 人工确认不通过

```text
人工不确认
  -> 记录人工意见
  -> 主流程 Agent 发起修订
  -> 测试分析与设计 Agent 修改用例
  -> 重新用例评审
  -> 再次等待人工确认
```

### 7.5 人工执行与报告生成

人工执行阶段由测试人员完成实际操作。系统只负责提供待执行用例、接收执行记录和保存证据，不在 V1 中自动判断没有证据支持的执行结果。

测试人员至少应记录：

- 用例编号和版本。
- 实际执行时间和环境。
- 执行结果：通过、失败、阻塞或跳过。
- 实际结果和与预期结果的差异。
- 关联缺陷编号。
- 截图、日志、录屏或其他证据路径。

## 8. 功能需求

### FR-01 项目初始化与需求导入

系统应支持创建一个测试项目，并导入需求文档、设计图、业务规则、约束说明等资料。

要求：

- 为每个项目生成唯一项目标识。
- 记录输入文件名称、类型、来源和导入时间。
- 保留原始文件，不覆盖原始资料。
- 支持用户查看当前流程状态和已有产物。

### FR-02 需求评审

系统应调用需求评审能力，输出结构化需求评审报告。

评审至少覆盖：

- 需求目标和范围是否明确。
- 业务流程和状态变化是否完整。
- 输入、输出和数据规则是否明确。
- 正常、异常和边界条件是否说明。
- 角色、权限和前置条件是否明确。
- 与已有规则是否冲突。
- 是否具备可测试性。

报告必须包含：问题编号、问题类型、严重程度、原文定位、问题说明、影响、修改建议和准入结论。

### FR-03 需求分析

只有需求评审通过后，系统才能进入需求分析。需求分析应将自然语言需求转换为结构化内容，包括：

- 业务目标。
- 参与角色。
- 主流程和分支流程。
- 状态及状态转换。
- 业务规则。
- 输入输出数据。
- 前置条件和后置条件。
- 异常处理。
- 权限约束。
- 待确认项和分析假设。

不确定内容必须显式标记为“待确认”或“假设”，不能伪装成已确认事实。

### FR-04 测试点与功能测试用例设计

系统应根据结构化需求分析生成测试点和功能测试用例。

测试点至少考虑：

- 正常流程。
- 异常流程。
- 边界值和空值。
- 参数组合和状态组合。
- 权限与角色差异。
- 重复操作、幂等性和并发风险（适用时）。
- 数据一致性和回滚。
- 兼容性和可用性（适用时）。

每条用例至少包含：

| 字段 | 说明 |
| --- | --- |
| case_id | 稳定的用例标识 |
| version | 用例版本 |
| requirement_refs | 关联需求条目 |
| test_point_refs | 关联测试点 |
| title | 用例标题 |
| priority | 优先级 |
| preconditions | 前置条件 |
| test_data | 测试数据 |
| steps | 操作步骤 |
| expected_results | 对应的预期结果 |
| tags | 场景、风险、角色等标签 |

### FR-05 用例独立评审

用例评审 Agent 应基于需求分析、测试点和用例进行独立评估，至少检查：

- 是否覆盖需求条目和测试点。
- 步骤是否可执行且顺序合理。
- 预期结果是否明确、可观察、可判定。
- 测试数据是否足够。
- 是否遗漏异常、边界、权限和状态场景。
- 是否存在重复、冲突、不可执行或无法追溯的用例。
- 优先级是否与风险匹配。

评审结果应分为通过、不通过或需人工判断，并对每个问题给出等级、定位、依据和建议。

### FR-06 用例修订与版本管理

系统应支持根据评审报告或人工意见发起用例修订。

要求：

- 修订产生新版本，不覆盖历史版本。
- 记录修订原因、来源、时间和影响范围。
- 重新评审时明确评审的是哪个用例版本。
- 能查看历史版本之间的变更摘要。

### FR-07 人工审批

以下节点必须支持人工确认：

- 需求评审结果需要产品确认时。
- 用例评审通过后的正式用例确认。
- 评审问题是否接受风险时。
- 测试报告结论发布前（可配置，V1 默认保留）。

人工审批记录至少包含：审批人、审批时间、审批结论、意见和对应产物版本。

### FR-08 执行结果录入

系统应允许测试人员按照已确认用例录入执行结果，并关联缺陷和证据。

系统不得把“没有执行记录”自动解释为“通过”。缺少必要证据时，应标记为信息不完整或待补充。

### FR-09 测试报告

测试报告应至少包含：

- 项目和需求范围。
- 测试环境和执行时间。
- 用例总数及通过、失败、阻塞、跳过数量。
- 按优先级、模块或标签统计的结果。
- 失败用例和关联缺陷。
- 阻塞项和未覆盖范围。
- 风险和遗留问题。
- 测试结论及结论依据。
- 需求、用例、执行记录和证据的追溯关系。

## 9. 产物与数据协议

### 9.1 产物目录建议

```text
projects/<project-id>/
├── input/                  # 原始需求及附件，只读
├── artifacts/              # 结构化产物和可读报告
│   ├── requirement-review/
│   ├── requirement-analysis/
│   ├── test-design/
│   ├── testcase-review/
│   ├── execution/
│   └── test-report/
├── evidence/               # 截图、日志、录屏等测试证据
├── decisions/              # 人工审批、风险接受和流程决策
└── workflow.json           # 当前状态和流程元数据
```

### 9.2 统一产物元数据

每类结构化产物都应包含以下公共字段：

```json
{
  "artifact_id": "唯一标识",
  "artifact_type": "产物类型",
  "project_id": "项目标识",
  "version": 1,
  "status": "draft",
  "source_artifacts": [],
  "created_by": "agent 或 user",
  "created_at": "时间",
  "updated_at": "时间"
}
```

Agent 之间优先传递结构化 JSON，而不是只传递一段自然语言总结。Markdown 用于人阅读，JSON 用于流程编排、校验和后续追溯。

### 9.3 产物状态

建议统一使用：

```text
draft       草稿
pending     等待评审或审批
approved    已通过
rejected    未通过
superseded  已被新版本替代
completed   已完成
```

## 10. 流程状态与转换规则

V1 建议采用显式状态机：

```text
REQUIREMENT_RECEIVED
  -> REQUIREMENT_REVIEWING
  -> WAITING_PRODUCT_REVISION       # 评审不通过
  -> REQUIREMENT_ANALYZING          # 评审通过
  -> TESTCASE_DESIGNING
  -> TESTCASE_REVIEWING
  -> WAITING_CASE_REVISION          # 用例评审不通过
  -> WAITING_HUMAN_APPROVAL         # 用例评审通过
  -> WAITING_MANUAL_EXECUTION       # 人工确认通过
  -> GENERATING_REPORT
  -> COMPLETED
```

补充规则：

- 每次状态转换必须记录触发者、时间、原因和输入产物版本。
- 状态转换前校验前置产物是否存在且状态正确。
- 状态转换失败时保留当前状态和错误信息，不得静默跳过。
- 重试应产生执行记录，不能覆盖失败记录。
- 人工拒绝或退回必须附带意见，意见作为下一轮 Agent 工作输入。
- 可配置最大修订轮次，超过后转人工处理，避免无限循环。

## 11. 权限与安全边界

### 11.1 最小权限

| 角色 | 读取原始需求 | 写入分析产物 | 修改正式需求 | 修改确认用例 | 写入报告 |
| --- | --- | --- | --- | --- | --- |
| 主流程 Agent | 是 | 保存流程产物 | 否 | 否 | 是 |
| 测试分析与设计 Agent | 是 | 是 | 否 | 只能生成新版本草稿 | 否 |
| 用例评审 Agent | 是 | 只能写评审报告 | 否 | 否 | 否 |
| 测试人员 | 是 | 是 | 由业务流程决定 | 是，需形成新版本 | 可确认 |
| 产品或需求提供方 | 查看相关产物 | 修改正式需求 | 是 | 否 | 否 |

### 11.2 安全要求

- 原始需求文件只读保存，任何 Agent 不得直接覆盖。
- 正式需求必须由产品或需求提供方修改。
- Agent 生成的内容必须标明来源和版本。
- 不默认读取生产环境凭证、真实用户隐私数据或敏感配置。
- 测试证据中的敏感信息应支持脱敏后再进入报告。
- 文件路径和工具调用应限制在当前项目目录内。

## 12. 异常与人工介入

系统应将以下情况转为人工处理，而不是继续猜测：

- 输入资料无法读取、格式不支持或内容明显不完整。
- 需求存在相互冲突且无法依据现有资料判断。
- Agent 输出无法通过 JSON Schema 校验。
- 评审连续多轮不通过。
- 人工意见与需求或用例存在未解决冲突。
- 测试执行结果缺少关键证据。
- 测试结论涉及风险接受或发布决策。

错误信息应包含：发生阶段、错误类型、相关产物、可重试性、建议动作和原始错误摘要。

## 13. 非功能需求

### 13.1 可追溯性

任何测试报告结论都应能够反查到对应的执行记录、测试用例版本、测试点和需求条目。

### 13.2 可恢复性

关闭 Codex 或中断会话后，重新打开项目应能从 `workflow.json` 恢复当前状态，并继续处理未完成节点。

### 13.3 可解释性

Agent 输出的问题、结论和建议应引用输入资料中的具体章节、段落、表格或文件位置。无法定位时必须明确说明依据不足。

### 13.4 一致性

同一项目中的需求、测试点、用例、评审和执行记录应使用稳定 ID 关联，避免仅依赖标题或自然语言名称。

### 13.5 可测试性

流程编排逻辑、状态转换、产物校验和主要 Skill 应可脱离大模型进行单元测试。大模型调用应支持替换为固定测试夹具。

### 13.6 成本控制

- 专业 Agent 只接收当前阶段所需的上下文和结构化产物。
- 大文件日志、截图和历史版本不应无条件全部塞入主会话。
- 用 Skill 解决稳定、单一、可复用的工作，不为每个小步骤创建新 Agent。
- V1 先采用串行流程，确认价值后再评估并行或更复杂编排。

## 14. 典型使用场景

### 场景 A：需求一次评审通过

测试人员导入“修改收货地址”需求，需求评审通过后，系统完成需求分析、测试点和用例设计，用例评审通过，测试人员确认并执行，最后生成测试报告。

### 场景 B：需求评审不通过

需求没有说明未登录用户、地址数量上限和保存失败时的处理方式。系统输出澄清清单并暂停，产品补充正式需求后重新评审。

### 场景 C：用例评审不通过

用例覆盖了正常保存，但遗漏地址上限边界和无权限用户。用例评审 Agent 输出问题，设计 Agent 生成新版本用例，系统重新评审。

### 场景 D：测试执行发现阻塞

测试环境依赖服务不可用，相关用例标记为阻塞并上传日志。测试报告应区分“未通过”和“无法执行”，不能把阻塞用例统计为失败或通过。

## 15. V1 验收标准

### 15.1 流程验收

- 能导入一个真实的小型需求并创建项目。
- 能从需求接收走到测试报告生成。
- 需求评审不通过时能暂停并回到产品修订环节。
- 用例评审不通过时能自动发起修订并重新评审。
- 人工确认不通过时能记录意见并重新进入修订流程。
- 流程中断后能恢复到最近一个可靠状态。

### 15.2 产物验收

- 每个阶段都生成对应的 JSON 结构化产物和 Markdown 可读报告。
- 测试点与用例存在明确关联。
- 用例包含前置条件、数据、步骤和可判定的预期结果。
- 评审问题包含严重程度、定位、依据和建议。
- 测试报告统计与执行记录一致。
- 所有产物保留版本，不覆盖历史记录。

### 15.3 安全验收

- Agent 不会修改正式需求。
- 用例评审 Agent 不会直接改写用例。
- 未通过需求评审时不会生成“正式确认用例”。
- 缺少执行证据时不会自动判定用例通过。
- 项目目录之外的文件不会被流程自动修改。

### 15.4 最小测试集

至少使用一个“新增或修改收货地址”的小型需求验证以下四条路径：

1. 需求一次评审通过，完整走到测试报告。
2. 需求评审不通过，产品修订后重新评审并通过。
3. 用例评审不通过，修订后重新评审并通过。
4. 人工确认不通过，提交意见后修订并重新评审。

## 16. 后续演进方向

V1 闭环稳定后，再按实际痛点逐步增加能力：

1. 接口自动化 Agent：依据接口文档和已确认用例生成、执行和维护接口自动化代码。
2. 测试执行接入：对接现有自动化框架、CI 或测试平台。
3. 缺陷管理接入：关联 Jira、禅道等系统。
4. 团队知识库：引入项目规范、历史缺陷和领域知识的检索能力。
5. 更复杂的并行编排：仅在任务量和耗时证明需要时引入。
6. Web 界面和多人协作：在本地原型验证价值后再建设。

## 17. 待确认问题

以下问题不阻塞需求文档定稿，但在技术设计前需要确认：

- 首个试点项目使用什么格式的需求文档：Markdown、Word、PDF 还是混合格式？
- 测试用例最终需要导出为 Markdown、Excel，还是接入现有测试管理平台？
- 用例字段是否需要兼容现有团队模板，例如模块、前置条件、步骤、预期结果、优先级和类型？
- 人工执行记录采用 Markdown/JSON 文件，还是需要先做简单表单？
- 首个试点需求及其验收标准是什么？
- 是否需要保留每次 Agent 调用的原始输入、输出和模型信息，以满足审计要求？
- 用例评审和测试报告发布是否必须指定审批人？

## 18. 一句话总结

本系统不是让一个 AI 包办全部测试工作，而是用明确的 Agent 分工、Skill 能力、状态机、结构化产物和人工审批，把测试流程变成可追踪、可恢复、可评审和可持续改进的工程系统。
